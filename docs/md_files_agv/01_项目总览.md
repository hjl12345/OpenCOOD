# 01 项目总览：OpenCOOD 是什么

## 1. 定位

**OpenCOOD**（**Open** **COO**perative **D**etection）是一个面向自动驾驶的**多智能体协同感知（multi-agent cooperative perception）**开源框架，同时是 ICRA 2022 论文 *OPV2V: An Open Benchmark Dataset and Fusion Pipeline for Perception with Vehicle-to-Vehicle Communication* 的官方实现。

严格来说，本仓库提供的是**三件东西**，而不是一个模型：

| 组成 | 内容 | 代码位置 |
|---|---|---|
| **数据 API** | OPV2V / V2XSet 两个协同感知数据集的统一读取、索引、坐标系变换、噪声模拟 | `opencood/data_utils/` |
| **融合流水线** | 早期 / 晚期 / 中间 三种融合范式的完整实现骨架 | `opencood/data_utils/datasets/` |
| **模型库** | 10 余种已发表协同感知方法的参考实现（统一以 PointPillar 为 backbone 便于公平比较） | `opencood/models/` |

它的设计目标不是「跑一个 SOTA」，而是**让新方法能以最小改动接入并公平对比**——这一点决定了它的架构（配置驱动 + 反射加载）。

---

## 2. 要解决的问题

单车 LiDAR 存在三个物理瓶颈：

1. **遮挡（occlusion）**：大型车辆、建筑遮挡导致目标点云缺失；
2. **稀疏（sparsity）**：远处目标的点云随距离平方衰减，40 m 外车辆往往只有几个点；
3. **视野受限（limited FOV）**：单车视角无法覆盖路口盲区。

协同感知的思路是：让附近车辆（CAV, Connected Automated Vehicle）或路侧单元（RSU, Roadside Unit）把**自身感知结果或中间特征**通过 V2X 通信共享，在自车（**ego**）处融合，从而等效扩展感知范围与点云密度。

代价是**通信带宽**与**位姿误差 / 时延**。这两个约束贯穿整个框架的设计：

- 带宽 → 决定了「传什么」（原始点云 / 特征 / 检测框）；
- 位姿误差与时延 → 决定了 `intermediate_fusion_dataset.py` 中大量看似冗余的坐标系与时间戳处理逻辑。

---

## 3. 三种融合范式

这是理解 OpenCOOD 的**第一性分类**。它不是模型层面的差异，而是**数据流层面的差异**，直接对应三个 Dataset 类。

| 维度 | 早期融合 Early | 晚期融合 Late | 中间融合 Intermediate |
|---|---|---|---|
| 传输内容 | 原始点云 | 检测框 + 置信度 | 深度特征图（BEV） |
| 融合时机 | 体素化**之前** | 检测**之后** | backbone **之后**、检测头之前 |
| Dataset 类 | `EarlyFusionDataset` | `LateFusionDataset` | `IntermediateFusionDataset` |
| 带宽（OPV2V, PointPillar） | 7.68 Mb | **0.024 Mb** | 72.08 Mb（压缩后 1.12 Mb） |
| AP@0.7（Default Towns） | 0.800 | 0.781 | 0.822（V2VNet） |
| 坐标系 | 全部投影到 ego | 各车在**自身**坐标系推理 | 可先投影点云（`proj_first`）或先提特征再 warp |
| 代表方法 | Cooper | Naive Late | Attentive Fusion / F-Cooper / V2VNet / V2X-ViT |

> 关键 trade-off：早期融合精度高但带宽不可接受；晚期融合带宽极低但丢失了原始信息、且无法利用跨车互补的raw signal；中间融合是当前主流，在「带宽可压缩」与「信息保真」之间取平衡。

**代码上的体现**：三种范式共享 `BaseDataset.retrieve_base_data()` 读盘逻辑，只在 `__getitem__()` 里分叉：

- `early_fusion_dataset.py`：把所有车的点云 `vstack` 后**只做一次** `preprocess`；
- `intermediate_fusion_dataset.py`：**每辆车各自** `preprocess`，输出特征列表 `processed_features`，再 `merge_features_to_dict` 合并；
- `late_fusion_dataset.py`：各车点云保持自身坐标系，**不做跨车投影**，推理时逐车 forward 再统一投到 ego 做 NMS。

## 4. 支持的模型谱系

| 模型 | 融合机制 | `model.core_method` | 融合模块文件 | 论文 |
|---|---|---|---|---|
| No Fusion | 单车基线 | `point_pillar_intermediate` | 无 | — |
| F-Cooper | 逐像素 max pooling | `point_pillar_fcooper` | `f_cooper_fuse.py` | SEC 2019 |
| Attentive Fusion | 空间维自注意力（每像素跨车） | `voxel_net_intermediate` / `pixor_intermediate` | `self_attn.py` | ICRA 2022 |
| V2VNet | 位姿引导 warp + ConvGRU 多轮消息传递 | `point_pillar_v2vnet` | `v2v_fuse.py` | ECCV 2020 |
| V2X-ViT | 异构多智能体注意力 + 多尺度窗口注意力 | `point_pillar_transformer` | `v2xvit_basic.py` + `hmsa.py` + `mswin.py` | ECCV 2022 |
| CoBEVT | FAX 融合轴向注意力 | `point_pillar_cobevt` | `swap_fusion_modules.py` | CoRL 2022 |
| Where2comm | 空间置信图驱动的**选择性通信** | `point_pillar_where2comm` | `where2comm_fuse.py` | NeurIPS 2022 |
| CoAlign | 多尺度特征 + 逐尺度 warp/attention（仅融合部分） | `point_pillar_coalign` | `coalign_fuse.py` | ICRA 2023 |
| V2VAM | 十字交叉注意力 + 双池化 | `point_pillar_intermediate_V2VAM` | `V2VAM.py` | TIV 2023 |
| FPV-RCNN | 两阶段（Proposal + RoI refine） | `fpvrcnn` | `fpvrcnn.py` | RAL 2022 |
| CIASSD | 3D 稀疏卷积 + SSFA 特征聚合（单阶段） | `ciassd` | `ciassd.py` | — |

> 阅读建议：**先吃透 V2VNet 与 V2X-ViT 两条主线**。前者是「显式几何对齐 + 迭代消息传递」的代表，后者是「隐式注意力对齐」的代表；其余方法基本是这两条路线的变体或折衷。
>
> 小勘误：README 的模型清单把 V2VNet 标成「ECCV2022」，实际是 **ECCV 2020**；CoAlign 在 README 里标注为「fusion only」，与本仓库实现一致。DiscoNet 与 AdaFusion 在 README 中为**未勾选**，本仓库没有实现。

> ⚠️ 三个容易误解的地方：
> 1. Attentive Fusion 在本仓库**只有 VoxelNet / PIXOR backbone 的配置**，PointPillar 下没有对应 yaml；
> 2. CoBEVT 的融合模块是 `swap_fusion_modules.py`（论文中的 FAX, fused axial attention），**不是** `sub_modules/vsa.py`——后者是 FPV-RCNN 的 `VoxelSetAbstraction`。
> 3. `point_pillar_intermediate_fusion.yaml` 指向的 `point_pillar_intermediate` 虽含 "intermediate" 字样，却**没有融合模块**，且因输出按车数组织（不回读 `record_len`）在多车场景下与损失维度不匹配，不宜当作 no-fusion 基线（详见 [05 §5.1](05_模型原理.md)）。

## 5. 统一 backbone：PointPillar

框架把「特征提取」与「特征融合」**解耦**，绝大多数模型复用同一套 PointPillar backbone（`opencood/models/sub_modules/`）：

```
点云 (N,4) → PillarVFE → 支柱特征 (P,64) → PointPillarScatter → BEV (B,64,ny,nx)
        → BaseBEVBackbone (FPN) → (B,384,ny/2,nx/2) → shrink → (B,256,H',W')
```

以 ±40 m 的配置为例：`(B,64,200,704) → (B,384,100,352) → (B,256,50,176)`；V2X-ViT / CoBEVT / Where2comm 用 ±38.4 m，`ny=192`，故为 `(B,64,192,704) → (B,384,96,352) → (B,256,48,176)`。

两个例外需要注意：**CoAlign 用 `ResBEVBackbone`（ResNet 风格）**，**`point_pillar_intermediate`（未接入任何融合）用 `AttBEVBackbone`（带自注意力的 BEV backbone）**，二者的输出通道与 FPN 结构都与 `BaseBEVBackbone` 略有差异。此外，Late Fusion 的 LiDAR 范围是 ±70.4 m，`nx=352`，因此检测头分辨率只有 `176×100`。

这样设计的好处是：**同一配置下换融合模块时，参数量、感受野、输入分辨率完全一致**，AP 差异可归因于融合策略本身，而不是 backbone 容量。代价是：想比较不同 backbone（VoxelNet / SECOND）时，必须连同 yaml 的 `voxel_size`、`preprocess.core_method`、`model.core_method` 一起换。

## 6. 术语表（读代码必备）

| 术语 | 含义 | 代码中的载体 |
|---|---|---|
| **scenario** | 一次 CARLA 仿真录制，对应一个文件夹（如 `2021_08_22_21_41_24`） | `scenario_database` 的一级 key |
| **CAV** | 参与协同的智能体（车或路侧单元） | `cav_id` 字符串 |
| **ego** | 当前帧的「主车」，融合结果的接收方与坐标系基准 | `cav_content['ego'] == True` |
| **RSU** | 路侧单元，**folder id 为负数**（如 `-1`） | `infra` 标志：`int(cav_id) < 0` |
| **timestamp** | 5 位数字帧号（如 `00078`），10 Hz | 文件名前缀，`timestamp_key` |
| **`record_len`** | 一个 batch 内每个样本实际参与的车辆数 | `(B,)`，来自 `cav_num` |
| **`pairwise_t_matrix`** | 车与车之间的相对位姿 `Ti→Tj`，用于特征 warp | `(B, L, L, 4, 4)` |
| **`spatial_correction_matrix`** | 补偿「投影时刻」与「接收时刻」ego 位姿变化的矩阵 | `(B, L, 4, 4)` |
| **`prior_encoding`** | 三通道先验：速度（/30 归一化）、时延帧数、V2V/V2I 标志 | `(B, L, 3)` |
| **`psm` / `rm`** | 分类得分图 / 回归图（anchor-based 检测头输出） | `(B, A, H, W)` / `(B, 7A, H, W)` |

## 7. 重要常量

```python
# opencood/data_utils/datasets/__init__.py:17-20
GT_RANGE = [-140, -40, -3, 140, 40, 1]   # 评估最终范围
COM_RANGE = 70                            # 协同通信距离门限（米），超出则该车被丢弃
```

```python
# opencood/data_utils/datasets/basedataset.py:373-376
# OPV2V / V2XSet 均为 10 Hz，因此 100 ms 折算为 1 帧
time_delay = time_delay // 100
```

`COM_RANGE = 70` 是一个**硬截断**：在 `__getitem__` 中，凡与 ego 平面距离 > 70 m 的 CAV 直接 `continue`，既不参与融合也不参与 GT 合并。这意味着同一个 scenario 在不同帧可能激活不同数量的车辆，因此 `record_len` 是**逐样本变化**的，不能被写成常量。

另外注意：`GT_RANGE` 只在**非训练模式**下生效。`base_postprocessor.py:129-130` 的分支是：

```python
filter_range = self.params['anchor_args']['cav_lidar_range'] if self.train else GT_RANGE
```

即训练期用 yaml 的感知范围裁剪 GT，**测试/验证期改用固定的 `GT_RANGE`（±140 / ±40）**；`box_utils.get_mask_for_boxes_within_range_torch` 也用 `GT_RANGE` 过滤预测框。这带来一个实际影响：若你的配置范围小于 `GT_RANGE`（如 Late Fusion 的 ±70.4），测试期 GT 不会被裁剪到 ±70.4，而是保留到 ±140——**评估范围与训练范围不一致**，是跨论文比较时的隐患。

## 8. 性能基准（摘自 README，便于对照）

OPV2V LiDAR track，PointPillar，AP@0.7（Default Towns / Culver City）。README 原表给的是「不压缩 / 压缩后」两组数字，下表**只取不压缩那一列**：

| 方法 | 带宽 (Mb) 压缩前/后 | Default Towns | Culver City |
|---|---|---|---|
| Naive Late | **0.024** / 0.024 | 0.781 | 0.668 |
| Cooper (Early) | 7.68 / 7.68 | 0.800 | 0.696 |
| F-Cooper | 72.08 / 1.12 | 0.790 | 0.728 |
| Attentive Fusion | 126.8 / 1.98 | 0.815 | 0.735 |
| V2VNet | 72.08 / 1.12 | 0.822 | 0.734 |
| CoAlign | 72.08 / 2.24 | **0.833** | 0.760 |
| FPV-RCNN | 0.24 / 0.24 | 0.820 | 0.763 |
| V2VAM | — | **0.860** | **0.813** |
| CoBEVT | 72.08 / 1.12 | **0.861** | **0.773** |

> 表中 `a / b` 表示「压缩前 / 压缩后」。压缩即 `model.args.compression > 0` 时启用的 `NaiveCompressor`（3×3 卷积编解码自编码器，把 256 通道压到 `256 // compression`），实现见 [05 §2.5](05_模型原理.md)。
